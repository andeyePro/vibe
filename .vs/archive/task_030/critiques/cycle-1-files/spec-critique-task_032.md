# Spec Critique — task_032

## Concerns

1. **BLOCKING (AC9–AC11, AC12).** The just-landed `site-check.mjs` parses an embedded `const COPY = {...}` blob out of an inline `<script>` (`parseCopy()`, line 64) and every task_030 guard (`chipBlock`, `linesFor`, `chipCmd`, `checklistLength`, `stepsContiguous`, the launch/first-launch/pat per-line checks) reads `COPY_DATA.lines`. That blob exists today only because `index.astro`'s client script types out `stepLines` line-by-line. Once chip-click becomes `seek({marker:i}); play()` on the player, there is no client-side reason to keep serialising `lines` into a `<script>` tag — the spec never says whether `const COPY = {...}` (or an equivalent parseable structure) must still be emitted. If the Generator drops it (a natural reading of "the pane changes"), `parseCopy()` throws on line 74, `node site-check.mjs` crashes with an uncaught exception before a single one of ~20 downstream checks runs, and AC12 fails outright — not a graceful per-check FAIL. The spec must pin down what structure the built HTML still exposes for these pre-existing assertions to parse, or explicitly authorise the Tester to replace `parseCopy()`/its dependents.

2. **BLOCKING (AC4, AC11, AC8-of-task_030).** `markers.json` is constrained to exactly the 13 top-level `data-step` ids, one marker each (AC4: "its ids equal the 13 ... same order"). But `stepsContiguous` (already in site-check.mjs) and the deck itself require *multiple* checklist ticks per chip (launch alone has 4 items, each keyed to a distinct line `step`). One marker per chip cannot reproduce that granularity through "the marker event ticks the matching checklist" (AC11, singular event → checklist, not per-item). Either markers.json needs sub-step entries beyond the 13 chip ids (contradicting AC4's exact-set wording) or the granular per-item ticking already tested by `stepsContiguous` is being silently dropped — the spec doesn't say which, and as written a spec-compliant Generator will produce either an AC4 violation or an AC10 regression.

3. **BLOCKING (Test location).** AC11 is the largest, most specific AC (six literal player-option values, the IntersectionObserver/dynamic-import lazy-load contract, chip→seek→play wiring, marker→tick wiring) but the "Test location" section assigns site-check.mjs only AC2–AC6 and AC8–AC10, and scrub.test.mjs only AC7. AC11 has no mechanical test owner — AC13 is explicitly Evaluator-only and fuzzy ("chips unlock/tick"), which won't catch a wrong `idleTimeLimit`, a missing `poster`, or a `<link rel="preload">` slipped into `<head>`. Add AC11 to the Tester's assertion list (e.g. grep the built `<head>` for absence of the vendor path; grep the page script/bundle text for the literal option strings and `IntersectionObserver`).

4. **BLOCKING (AC8/AC12 interaction).** `npm run check` runs `astro build && node site-check.mjs` — it invokes the `astro` binary directly, not `npm run build`. npm's `prebuild` lifecycle hook only fires automatically ahead of a script literally named `build` run via `npm run build`; it does not fire for a different script (`check`) that happens to shell out to `astro build`. As specified, `node scripts/vendor-player.mjs` (AC8's `prebuild`) will never run under the AC12 gate command, so `site/public/vendor/*` won't exist and the gzip-size checks (and the runtime `import()`) will fail. Either `check` must become `npm run build && node site-check.mjs`, or vendoring must be wired into `astro build` itself (Astro integration hook) — the spec doesn't say which, and this isn't something the Generator can silently decide since it changes `package.json` in a way not called out anywhere.

5. **MINOR (AC10 scope).** AC10's guarantee is explicitly narrowed to "inBoth guards," but the pre-existing `'terminal height is viewport-bounded'` check (a raw regex on `.term-body{...height:clamp(...)}` CSS) and the exact-13-chips/checklist-count checks are not inBoth guards, yet AC12 needs them to keep passing too. If the new player mount doesn't reuse the `.term-body` class name, this check fails with no clear authorisation for Tester or Generator to touch it.

6. **MINOR (AC9).** "`id=\"cast\"` or similar" is vague enough that the Tester may write an assertion against a name the Generator didn't pick; recommend fixing the id in the spec (Generator owns the component either way, so pin it).

7. **Verified, no issue:** asciicast v2 genuinely defines `"m"` and `"r"` events (confirmed against the v2 spec, not v3-only as the brief worried); `poster: 'npt:0:0'` and `fit: 'width'` are valid player options (`'width'` is actually the library default, so listing it is redundant but harmless); the six AC6 strings and the AC1 placeholder-synthesis inputs all exist verbatim in `home.md`/`vibe`/`init-firewall.sh` after dash-normalisation; `home.md`'s deck lines contain no `@` at all, so AC5's email regex has no placeholder false-positive to worry about this cycle.
