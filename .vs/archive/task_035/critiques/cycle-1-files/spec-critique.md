# Spec Critique — task_035, cycle 1

## Concerns

1. **AC10 — BLOCKING.** "The Tester runs this once as the decisive check" against the *full* `smoke-test.py` (480+ tests, 15,330 lines, per CLAUDE.md "takes several minutes"; spec's own estimate 4–25 min under load) with an inherited open pipe on stdin. The Bash tool's hard cap is 600s (10 min) max. Any run over ~10 min — plausible even on correctly-fixed code under load — gets killed by the tool itself, producing an ambiguous timeout that AC10 cannot distinguish from "the fix didn't work." Worse, if the stdin-inherit bug is NOT actually fixed, this is exactly the failure mode that caused the original 55-minute hang task_035 exists to prevent — now baked into the acceptance test. AC10 should be the targeted AC4 child (a single small representative spawn) run under an inherited pipe, not the whole suite; `python3 smoke-test.py < /dev/null` (the other AC10 clause) already covers the full-suite regression at the normal, bounded runtime.

2. **AC6 — BLOCKING, concrete false positive.** `checks_11_patrotation_and_firewall.py::test_gh_meta_rate_limit_and_cache_fallback` (dated 2026-09-02, i.e. today) is a second live INIT_FIREWALL-sourcing test that does **not** go through `_fw_run`: it hand-builds `env = {**os.environ, "PATH": ..., "STUB_LOG": ..., **base_env}` (`base_env = {"GH_META_CACHE": str(cache)}`) and calls `run(["bash","-c", f"source {shlex.quote(str(INIT_FIREWALL))}\n..."], env=env)` ~15 times. It is safe today (it isolates the one relevant knob, GH_META_CACHE, by hand) but under AC6's literal rule ("fails on any `env=` at those call sites not routed through `_isolate_extras_env`/`_fw_run`") this legitimate test trips the new lint. The spec's task summary names only `_fw_run`'s inline `GH_META_CACHE` as the offender and doesn't flag this second call site — it's one of "the other twelve files" the summary alludes to but doesn't name. Generator scope note ("spawn sites across checks_*.py") is broad enough to cover the needed refactor (wrap `env` through `_isolate_extras_env`; its `env.setdefault` won't clobber the explicit `GH_META_CACHE` already in `base_env`), but this should be called out explicitly so it isn't discovered as a surprise mid-cycle.

3. **AC5 — MINOR, contamination risk under-specified.** `_isolate_extras_env` allocates one process-global `_EXTRAS_SCRATCH_HOME` shared across every call. If its GH_META_CACHE default also lives under that single shared scratch dir (as opposed to a fresh path per call), any `_fw_run` invocation that does NOT override it afterward would share one cache file across the whole test run — a real risk of one test's successful fetch poisoning a later test's fail-closed assertion. AC5's own text does allow "a test may override AFTER calling it," and `_fw_run` should exercise exactly that (keep its current `tmp / "gh-meta-cache.json"` override after calling the builder) — but the spec should say so explicitly rather than leaving it inferable, since "consumes it instead of setting its own" reads as the opposite.

4. **AC9 — MINOR, semantic narrowing not called out.** `site/.gitignore`'s un-anchored `node_modules/`/`dist/`/`.astro/` (no leading slash — matches at any depth under `site/`) are removed as "duplicates" of root's `site/node_modules/` etc. (slash-containing, anchored to repo root, matches only the top-level dir). For a nested `site/**/node_modules` this is a real narrowing of ignore coverage, not a pure duplicate removal — low practical risk for an Astro site with no npm workspaces, but the "byte-identical duplicate" framing overstates equivalence. `public/vendor/` as the sole unique survivor line is verified correct (root has no `vendor` reference at all).

5. **AC3 — MINOR, implementation-fragility risk, not spec ambiguity.** Today's raw `subprocess.run/Popen/check_output` count in `smoke/*.py` is 48 (well above the ≥20 floor — not vacuous now). But nothing in AC3 requires AST-based per-call argument scanning; a naive line-window regex risks both false negatives (a violating call's missing `input=`/`stdin=` masked by an unrelated nearby call's `input=` on an adjacent line, e.g. the multi-line calls at `checks_04_hooks_guards.py:1131/1193`) and false positives. Recommend the spec require (or at least strongly suggest) `ast.parse`-based Call-node inspection for AC3/AC6 rather than leaving the matching strategy to the Tester's discretion.

## Verdict

**revise** — concerns 1 and 2 are blocking: AC10 as written can fail the correct implementation for reasons unrelated to the fix (Bash-cap timeout), and AC6 as written will trip on a legitimate, already-safe test (`test_gh_meta_rate_limit_and_cache_fallback`) that the spec doesn't name as in-scope. Both are fixable with small spec edits (narrow AC10's target, name the second INIT_FIREWALL call site explicitly).
