# Spec Critique — task_050 `codex-panel.mjs` (spec-draft-codex-panel.md)

## Concerns

1. **AC5, BLOCKING — the pinned glob is wrong for real Codex filenames.** `rollout_file_name.rs::render()` puts the timestamp FIRST: `rollout-<YYYY-MM-DDTHH-MM-SS>-<thread_id>.jsonl` (or `..._<rollout_id>.jsonl` for a reverted thread). `thread_id` is never a filename *prefix* — `$CODEX_HOME/sessions/**/<thread_id>*.jsonl` therefore matches nothing a real Codex build ever writes; every live `--verify` run would resolve `nonce_check: "rollout-not-found"` and always exit 1. The task explicitly asked for this glob to be "pinned rather than guessed" from `rollout/src/lib.rs` — it was guessed. Correct shape: `rollout-*-<thread_id>*.jsonl` (allow the `_<rollout_id>` tail), under `sessions/YYYY/MM/DD/` (confirmed via `list.rs::rollout_date_parts`, so `**` is right there). Also unaddressed: `compression.rs` gives every rollout a `.jsonl.zst` sibling — the glob needs `{.jsonl,.jsonl.zst}` or the AC must say reads always happen before compression and why that's guaranteed.

2. **AC5/AC7, BLOCKING — stub complicity makes the bug in #1 untestable by design.** The smoke fixture "writes a fake rollout ... under the fixture `CODEX_HOME/sessions/`" using whatever path shape the same author's implementation expects. Nothing requires the fixture's filenames to be built independently from the real `render()` format. As drafted, AC7 can go fully green while the live path is broken — exactly the "stub agrees with production's own wrong assumption" failure mode the task asked me to hunt for. Fix: state the exact filename template in AC5 itself (not "confirmed... and documented in the script header" after the fact) and require the AC7 fixture to construct paths via that literal template, independently of the code under test.

3. **AC2, BLOCKING — "symmetric difference of the two recorded vectors" is weaker than the pattern it claims to reuse, and is a contradiction.** `checks_01`'s actual "golden-plus-one-addition" pattern (`TASK034_GOLDEN_DEVCONTAINER_RENDER_OP_OFF` test) asserts ordered LIST equality (`golden + [new_entry] == current`), not a set/symmetric-difference. A literal `set(a) ^ set(b)` test is blind to duplicates, order, and count: an implementation that appends `--ephemeral` a second time in ship mode (or drops+re-adds a flag with the same string) still reports symmetric difference `{'--ephemeral'}` and passes. Pin exact ordered-list equality (ship == verify with `--ephemeral` inserted/removed at one specific index), matching the precedent actually cited.

4. **AC2/AC4, BLOCKING — undefined argv/CLI failure surface invites silent divergence.** No range-validation behaviour is specified for `--n` outside `2..5` (0, 1, 6, 100, non-numeric, omitted) — contrast `vs.md`'s explicit clamp/round rules for `--panel`. AC7's test list never mentions n-validation either, so an implementation that happily spawns `--n 100` or crashes ungracefully on `--n 0` is untested either way. Exit codes are also inconsistently pinned: AC1 nails "exit 2" for bad stdin and non-worktree, but the `codex=off` refusal and readiness failures (version floor, login probe) are only "non-zero" — leaves 1 vs 2 vs 3 to the implementer with no test able to catch drift either way.

5. **AC4, BLOCKING — "validated against the delegate's REVIEW schema" silently drops the delegate's semantic check.** `vibe-delegate.mjs` codex() rejects `verdict: PASS` with a `BLOCKING` finding as an invalid reply (lines ~175-177) — that's not part of the `REVIEW_SCHEMA` JSON-Schema object AC4 names, it's separate post-parse logic. AC4 doesn't say whether the panel re-applies that consistency rule per reviewer. As drafted, a reviewer returning `PASS` + a `BLOCKING` finding is schema-valid and silently counts toward `tally.PASS`, corrupting exactly the tally the chair's correlated-agreement check depends on (`vs.md` § Step 5c).

6. **AC5/D6 interaction, MINOR-to-BLOCKING — real, shared `$CODEX_HOME` retains full diff content after every live `--verify` run, unaddressed.** `docs/codex-integration-plan.md` D6 explicitly rejects distinct `CODEX_HOME`s ("would require copying `auth.json`, which vibe never does") — so verify mode's N reviewers, lacking `--ephemeral`, all write real rollout files into the user's actual `~/.codex/sessions`, each containing the full diff plus that reviewer's nonce, indefinitely. Task summary line 5 name-checks D6 for the isolation rationale but the spec never reconciles this with the TODO mandate's literal phrase "distinct Codex homes/session stores" (which D6 explicitly can't deliver) — nor states any retention/cleanup expectation for these on-disk artifacts. Needs one explicit sentence either way.

7. **AC3, MINOR — concurrency assertion is only as strong as an unstated stub delay.** "asserts overlap via the stub's start/end timestamps" is vacuous unless the stub sleeps long enough that a sequential implementation could *not* produce overlapping windows by timer-resolution luck. Pin a minimum artificial stub delay (e.g. ≥150ms) so the overlap check actually discriminates concurrent from serial dispatch.

8. **AC6, BLOCKING — zero mechanical coverage for a named acceptance criterion.** AC7's test enumeration covers every other AC but never mentions verifying the `vs.md` line-count cap, the README sentences, or the `docs/codex-integration-plan.md` D6 edit. In a rigorous-mode `/vs` run (Tester is mechanical-only per `vs.md` § Step 5), AC6 can be skipped entirely with a fully green suite. The repo already has precedent for this exact gap (`test_review_command_docs` was defined-but-unregistered per TODO.md's own "unregistered test functions" item) — don't repeat it. Add a grep-based doc-length/substring check to AC7.

9. **AC1, MINOR — readiness-probe process count is unaccounted for.** `codexReady()` itself spawns `codex --version` and `codex ... login status` — extra vendor processes beyond the N review processes. AC7 promises to assert "N processes" but doesn't say whether readiness probes run once (shared) or N times (once per reviewer); either is plausible from the prose, and the stub's process-count assertion can't tell them apart without saying which is intended.

## Verdict

**revise**

Concerns 1–5 and 8 are BLOCKING: #1+#2 together mean the live nonce proof (the entire point of `--verify`) is spec'd to fail in reality while its own test suite stays green; #3 is a factually wrong citation of an existing pattern; #4, #5, #8 leave mechanically-checkable behaviour undefined, which for a rigorous-mode `/vs` task means Generator and Tester can legitimately diverge from intent while `smoke-test.py` stays green.
