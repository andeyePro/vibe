## Deviation — one frozen task_026 test regresses (expected, spec-caused)

`test_task026_c2_pat_no_arg_refuses_invalid_detected_slug`
(smoke-test.py:11605) fails 2 of its 4 checks:

```
✗ stderr refusal names the detected slug
✗ stderr refusal says not a valid owner/repo
  (actual: "vibe pat: couldn't detect a GitHub repo here — pass one
  explicitly: vibe pat <owner/repo>")
```

Root cause: this test's fixture origin is
`https://github.com/ow+ner/repo.git`. Under the OLD `detect_github_repo`
regex (`[^/]+/[^/.]+`), the `+` in the owner segment was tolerated —
`detect_github_repo` returned `ow+ner/repo`, and `pat_handle_subcommand`'s
own downstream `is_valid_repo_slug` re-check (vibe ~565, comment: "detect_
github_repo's regex is looser than is_valid_repo_slug") then caught it and
printed the slug-naming refusal the test asserts on.

The pinned task_027 algorithm folds that same `is_valid_repo_slug` gate
**into** `detect_github_repo` itself ("return the slug ... ONLY if
is_valid_repo_slug passes; otherwise return 1"). So `detect_github_repo`
now returns 1 for `ow+ner/repo` directly — `pat_handle_subcommand`'s no-arg
branch takes the "couldn't detect a GitHub repo here" path instead, and its
downstream `is_valid_repo_slug` re-check (still present, unedited — out of
scope for this task) is now unreachable dead code.

This is NOT a security regression: an invalid detected slug still can't
reach `rotate_token`/`save_token` either way (checks 1 and 3 of that test —
exit 1, empty stdout — still pass). Only the two message-wording assertions
fail, because the failure now surfaces one branch earlier with a more
generic message. I did not edit `pat_handle_subcommand` or the frozen test
— both are explicitly out of scope for this Generator (Files in scope for
`vibe` lists only detect_github_repo/`_usage_text`/`refresh_brain2_vibe_note`/
call-site; test_task026_* is a previously-frozen, non-task_027 test I have
no license to touch). Flagging for the Tester/Chair: either retire/loosen
this specific message-wording assertion, or accept the dead branch and its
stale comment as a follow-up cleanup — the pinned-contract algorithm change
is unambiguous and I implemented it as specified.
