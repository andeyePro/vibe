# Spec — task_036: `--spec-first` for /vs (+ `--approve`, passthrough in /vss and /vsss)

## Task summary
Martin's queue item 1 (2026-09-04): "the harness writes the spec and then STOPS and waits for Martin to read and approve it before any code is written." Today `/vs` Step 3 waits for approval only inside an interactive session; under `/vss`/`/vsss` the executor approves acts-as-user, so the spec is never a checkpoint. `--spec-first` makes the checkpoint real and resumable: Steps 1–3 run, the spec + TODO entry + a `tasks.json` status `awaiting-approval` are committed, a plain-English summary prints, and the run ENDS with no Generator. `/vs --approve [<task-id>]` continues from Step 4; Martin's edits to `.vs/spec.md` ARE the approved version (never byte-identity, never a re-critique; one exception: an edit raising the Model plan to a credit-billed tier needs a fresh ask). `/vss`/`/vsss` pass the flag through; under `/vsss` a spec-first item never blocks the loop — it posts one fromClaude action point and moves on; an `approve` answer queues `/vs --approve <task-id>` as a later iteration's item. Out of scope: any PreToolUse edit-blocking hook (safety floor; later hardening). Baseline 735ca85.
